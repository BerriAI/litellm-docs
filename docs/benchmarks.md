# Benchmarks

Benchmarks for LiteLLM Gateway (Proxy Server) tested against a fake OpenAI endpoint.


LiteLLM Gateway has **8ms P95 latency** at 1k RPS (See benchmarks [here](#4-instances))

## v1.102.0: 3,000 rps with 50k to 100k-token prompts

This benchmark measures the [high-throughput gateway profile](./proxy/high_throughput.md) of the componentized Helm chart (`1.102.0-dev.2`) against `v1.101.0` on a large-prompt workload, the shape of agentic coding traffic rather than the short chat bodies used in the older sections below. Both runs used the same distributed Locust rig (a master and 30 workers) through a public AWS ALB: 3,000 simulated users at one request per second each, `/v1/chat/completions` bodies of 50k, 75k, and 100k tokens in equal shares, `max_tokens: 16`, 50 percent of requests with `stream: true`, virtual-key auth on a key with a `max_budget` so budget reservation and admission token counting run, and an in-process mock model so the gateway does all the work the real request path does (auth, budget, token counting, spend, metrics) without provider spend or provider latency. Response caching was disabled for the mock model. The Locust client timeout was 60 seconds.

The patched build ran `LITELLM_RUST=1`, PgBouncer with 8 upstream connections per pod, the metrics and collector sidecars, four workers per pod on a 4 vCPU request with a 16 vCPU limit and 16Gi, and the RPS/TPS HPA, which settled at 33 pods. `v1.101.0` ran the existing production-shaped deployment: 132 pods of one worker each at 2 vCPU and 4Gi with a fixed replica count. That is 132 workers on both sides, 528Gi of requested memory on both sides, and 132 requested vCPU for the patched build against 264 for `v1.101.0`. The patched run lasted 24 minutes 22 seconds (4,381,143 requests) and the `v1.101.0` run 5 minutes 7 seconds (64,543 requests).

| Category | Metric | Patched (`1.102.0-dev.2`) | `v1.101.0` | Change |
|---|---|---:|---:|---:|
| Deployment | Gateway pods | 33 | 132 | 4x fewer |
|  | Workers per pod | 4 | 1 | |
|  | Total workers | 132 | 132 | same |
| Throughput | Requests/sec | 3.00K | 0.19K | 16x |
|  | Tokens/sec | 224.61M | 6.92M | 32x |
|  | Projected tokens/30 days | 582.20T | 17.94T | 32x |
| Reliability | HTTP 200 rate (Locust) | 100.00% (0 of 4,381,143 failed) | 92.07% (5,118 of 64,543 failed) | |
| Request latency (gateway) | p50 | 30.581 ms | 6.950 s | 227x |
|  | p95 | 54.029 ms | 27.451 s | 508x |
|  | p99 | 91.645 ms | 29.826 s | 325x |
| TTFT (client, Locust) | p50 | 31.667 ms | 9.400 s | 297x |

Throughput, tokens per second, projected tokens, and request latency are the gateway-side Prometheus headline stats (`litellm_proxy_total_requests_metric_total`, `litellm_total_tokens_metric_total`, and `litellm_request_total_latency_metric`) over each run. Projected tokens is tokens per second times 30 days. Client TTFT is the Locust `TTFT` row for streaming requests (exported by the Locust Prometheus exporter as `locust_requests_current_response_time_percentile_50{method="TTFT"}`), timed from sending the request to the first SSE data chunk, so it includes uploading the body over the ALB and admission; the gateway's own `litellm_llm_api_time_to_first_token_metric` only covers the provider call and reads a few milliseconds on a mock model, so it is not the number shown.

The HTTP 200 rate comes from the Locust reports and not from the gateway, because the gateway can only count requests it answered. On `v1.101.0` the 5,118 failures were 4,546 with HTTP status 0 (the Locust client timed out at 60 seconds or the connection dropped), 457 HTTP 504 and 115 HTTP 502 generated by the ALB; none of these reached the gateway, so its own success metric read 100 percent for that run while 7.93 percent of requests failed from the client's point of view. For the same reason the `v1.101.0` client-side p95, p99, and maximum response times sit at exactly 60,000 ms, the timeout, and the gateway-side latency histogram is the one shown in the table for both builds. Read Locust throughput from the `POST` rows: each streaming request also records a `TTFT` row, so the `Aggregated` line in a report with 50 percent streaming counts about 1.5 entries per real request.

The two runs differ in duration and in pod shape, so treat the table as a before and after of the profile as a whole rather than a controlled comparison of one variable. The per-change attribution below comes from separate A/B stages run on the patched build at 200 to 1,000 rps with one setting changed at a time.

Rust admission token counting with the byte-level fast path (`LITELLM_RUST=1`) cut the per-request count on 50k, 75k, and 100k bodies from 46, 53, and 100 ms to 4.9, 6.8, and 10.2 ms. Fleet-wide at 1,000 rps that moved gateway CPU per request from about 170 ms to about 23 ms, p95 from 730 to 300 ms, p99 from 880 to 360 ms, the settled pod count from 65 or more to between 11 and 29 depending on the run, and the gateway working set from 262 GiB to between 28 and 70 GiB. It is the change that made the workload fit the available compute. The Python tokenizer path measured 84 to 197 ms per body on the same inputs.

PgBouncer per pod (`database.connectionPool`) held Postgres at 86 to 175 connections for 11 to 29 pods and 218 to 227 at 65 or more pods, against the 880 to 5,200 that per-worker Prisma pools would have opened at the same replica counts. The pool console showed zero waiting clients and an average wait of 1 microsecond under the 1,000 rps soak. No run was made without the pool on this workload, so there is no latency comparison for it.

The collector sidecar (`gateway.collector`) removed the spend pipeline from the inference workers (py-spy inclusive share of the success handler 3.9 percent to about zero) and, at 700 rps, took p99 from 1,800 to 830 ms and the maximum from 6,375 to 2,870 ms, while adding 3.7 to 4.2 CPU cores fleet-wide for the sidecars, about 4 ms per request. Total compute at 700 rps was unchanged, so it is a tail-latency and isolation change, not a compute saving.

The metrics sidecar (`gateway.metricsServer`) cost about 2 millicores per pod at 700 rps and keeps every Prometheus scrape off the inference workers by construction; it was not measured against in-worker scraping.

Raising the gateway CPU limit from 4 to 16 while leaving the request at 4 took the CFS throttled-period ratio from 0.27 to 0.39 down to zero and p99 at 700 rps from 830 to 670 ms.

`KEEPALIVE_TIMEOUT=75` on the gateway (uvicorn `--timeout-keep-alive` above the ALB's 60 second idle timeout) took ALB-generated 502s at 200 rps from 15 (99.981 percent success) to zero.

Emitting the admission-time usage on streaming mock responses (v1.102.0) brought streaming mock requests, previously three to four times slower than non-streaming because the prompt was re-tokenized after the stream, to within about 30 ms of non-streaming, which is what allowed the 50 percent streaming mix at no extra CPU. This only affects mock responses and load testing, not real provider traffic.

The RPS/TPS HPA (`gateway.hpa.targetRequestsPerSecond` and `targetTokensPerSecond`) added a replica within about 48 seconds of a 200-user load step in a scale-out check. No controlled comparison against a CPU-only HPA was run.

Eight workers per pod instead of four gave no latency change at 700 rps and 50 percent more memory, and a tuned Python GC threshold gave no CPU change at 30 rps; both were reverted and are not part of the profile.

## Setting Up Benchmarking with Network Mock

The fastest way to benchmark proxy overhead is using `network_mock` mode. This intercepts outbound requests at the httpx transport layer and returns canned responses, no need for setting up a mock provider. 

**1. Create a proxy config:**

```yaml
model_list:
  - model_name: db-openai-endpoint
    litellm_params:
      model: openai/{{openai_large}}
      api_key: "sk-fake-key"
      api_base: "https://api.openai.com"

litellm_settings:
  network_mock: true
  callbacks: []
  num_retries: 0
  request_timeout: 30

general_settings:
  master_key: "sk-1234"
```

**2. Start the proxy:**

```bash
litellm --config benchmark_config.yaml --port 4000 --num_workers 8
```

**3. Run the benchmark script:**

```bash
python scripts/benchmark_mock.py --requests 2000 --max-concurrent 200 --runs 3
```

Get the benchmarking script [here](https://github.com/BerriAI/litellm/blob/main/scripts/benchmark_mock.py)

This measures pure proxy overhead on the hot path without any network latency to a real or fake provider.

## Locust Settings

- 1000 Users
- 500 user Ramp Up
- `wait_time = between(0.5, 1)`, so every user sleeps 0.5s to 1s between requests

### Why the think time matters when you reproduce these numbers

A Locust user spends its time either waiting on a response or sleeping. With a 0.75s mean think time and ~110ms responses, each of the 1000 users completes a request about every 0.86s, so the run offers ~1160 RPS and holds roughly **130 requests in flight** at any instant. That in-flight depth, not the user count, is what the latency columns above describe.

A closed-loop client with no think time is measuring something else. 1000 concurrent workers that send the next request the moment the previous one returns hold **1000 requests in flight**, about 8x the queue depth of these runs. Once a gateway is saturated its throughput is fixed, and by Little's Law the latency each client observes is just `requests in flight / throughput`. So the same deployment, at the same RPS, reports roughly 8x the latency purely because the client queued 8x as much work into it. Latency and concurrency are not independent, and neither number means anything without the other.

To compare against the tables above, either keep the 0.5s to 1s think time, or hold your client's in-flight request count near 130 and report it alongside the latency. It is also worth reporting RPS first: if your run shows higher RPS and higher latency than these tables, your gateway is faster than this benchmark and your client is simply queueing deeper.

## How to measure LiteLLM Overhead

All responses from litellm will include the `x-litellm-overhead-duration-ms` header, this is the latency overhead in milliseconds added by LiteLLM Proxy.


If you want to measure this on locust you can use the following code:

```python showLineNumbers title="Locust Code for measuring LiteLLM Overhead"
import os
import uuid
from locust import HttpUser, task, between, events

# Custom metric to track LiteLLM overhead duration
overhead_durations = []

@events.request.add_listener
def on_request(request_type, name, response_time, response_length, response, context, exception, start_time, url, **kwargs):
    if response and hasattr(response, 'headers'):
        overhead_duration = response.headers.get('x-litellm-overhead-duration-ms')
        if overhead_duration:
            try:
                duration_ms = float(overhead_duration)
                overhead_durations.append(duration_ms)
                # Report as custom metric
                events.request.fire(
                    request_type="Custom",
                    name="LiteLLM Overhead Duration (ms)",
                    response_time=duration_ms,
                    response_length=0,
                )
            except (ValueError, TypeError):
                pass

class MyUser(HttpUser):
    wait_time = between(0.5, 1)  # Random wait time between requests

    def on_start(self):
        self.api_key = os.getenv('API_KEY', 'sk-1234567890')
        self.client.headers.update({'Authorization': f'Bearer {self.api_key}'})

    @task
    def litellm_completion(self):
        # no cache hits with this
        payload = {
            "model": "db-openai-endpoint",
            "messages": [{"role": "user", "content": f"{uuid.uuid4()} This is a test there will be no cache hits and we'll fill up the context" * 150}],
            "user": "my-new-end-user-1"
        }
        response = self.client.post("chat/completions", json=payload)
        
        if response.status_code != 200:
            # log the errors in error.txt
            with open("error.txt", "a") as error_log:
                error_log.write(response.text + "\n")
```

*Lower is better for latency metrics; higher is better for requests and RPS.*

### Technical Insights

**Portkey**

**Pros**

* Low memory footprint
* Stable latency with minimal spikes

**Cons**

* CPU utilization capped around ~40%, indicating underutilization of available compute resources
* Experienced three I/O timeout outages

**LiteLLM**

**Pros**

* Fully uses available CPU capacity
* Strong connection handling and low latency after initial warm-up spikes

**Cons**

* High memory usage during initialization and per request
